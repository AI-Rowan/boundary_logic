# Boundary Logic — Implementation Summary

**Package:** `boundarylogic`
**Branch:** `paper_nr1_changes` (development continues on `method_developments`; `main` is the stable release)
**Last updated:** 2026-10-29

---

## 1. Purpose and Scope

The `boundarylogic` package operationalises a PhD research methodology for post hoc interpretability of binary classification models. The core idea is that a two-dimensional biplot projection of high-dimensional data preserves enough geometric structure to:

- approximate model decision boundaries in the reduced space;
- identify the nearest boundary-crossing point (counterfactual) for any observation;
- explain which variable changes drive the prediction across the boundary; and
- support both local (single observation) and global (full dataset) interpretability analyses.

This document records: the package file structure, the function inventory, how each component maps to the instruction manual modules A–G, and the key design decisions made during implementation.

## 3. S3 Class Hierarchy

Each phase produces a named S3 object. Later phases consume objects from earlier phases, forming a chain:

```
bl_data              (from bl_wrap_data())
  │
  ├─► bl_filter_result   (from bl_prepare_data() or bl_filter_outliers())
        └─► bl_model
              └─► bl_projection
                    └─► bl_grid
                          └─► bl_result          ← Phase 1 anchor
                                ├─► bl_points     (bl_project_points; bl_predict returns a data.frame)
                                │
                                ├── PHASE 2 (global) ─────────────────────────
                                ├─► bl_boundary   (bl_find_boundary)
                                ├─► bl_surrogate  (bl_surrogate)
                                │
                                └── PHASE 3 (local) ──────────────────────────
                                    ├─► bl_target        (bl_select_target; carries class_obs)
                                    ├─► bl_filters       (set_filters)
                                    ├─► bl_local_result  (bl_find_local_cf)
                                    │     └─► bl_counterfactual (bl_local$bl_counterfactual)
                                    ├─► bl_shapley       (bl_shapley)
                                    └─► bl_sparse_result (bl_find_sparse_cf)
```

`bl_build_result(bl_model = NULL)` also returns a `bl_result`, without a `bl_model` or `bl_grid` (the model, grid and contour fields are `NULL`).

All objects have `print()` methods. Objects with visual outputs have `plot()` methods.

## 4. Module-by-Module Function Inventory

### 4.1 Module A — Data Preprocessing and Model Fitting
*Instruction manual §3A*

**`R/data_prepare.R`**

| Function | Signature | Returns |
|---|---|---|
| `bl_prepare_data()` | `(data, class_col, target_class=NULL, feature_cols=NULL, train_fraction=0.8, seed=121L, hull_fraction=0.9, verbose=TRUE)` | `bl_filter_result` |
| `bl_wrap_data()` | `(train_data, test_data=NULL, var_names=NULL, target_class=NULL)` | `bl_data` |
| `bl_set_scaling()` | `(x, center, scale, method="z-score")` | same class as `x` (`bl_data`/`bl_filter_result`) |
| `bl_apply_scaling()` | `(data, bl_result)` | `data` with feature columns in model units |

`bl_prepare_data()` is the standard in-package ingestion path: converts multiclass factors to binary 0/1 indicators, makes a seeded simple random train/test split (`sample()`, not stratified), then calls `bl_filter_outliers()` internally to remove outliers and returns a `"bl_filter_result"`. The `hull_fraction` parameter (default `0.9`) controls how aggressively the convex hull trims the outermost training points; `hull_fraction = 1` retains all points.

`bl_wrap_data()` is the external-data path: accepts pre-split, pre-coded data and returns a `"bl_data"` object with no outlier filtering. Use it when the data and model are prepared outside the package.

`bl_set_scaling()` records a **display-only** per-feature affine transform `standardised = (raw - center) / scale` on a `bl_data` / `bl_filter_result` object, stored as `x$scaling = list(center, scale, method)` (both vectors named and ordered to `var_names`; a private `.align_scaling_vec()` helper validates finiteness, rejects zero scales, and reorders named or unnamed input). Use it when features were standardised *before* model fitting (common for SVM/NNET/logistic) so the biplot axes can later be relabelled into the original units. The scaling propagates through `bl_filter_outliers()` (pass-through) and `bl_assemble()` into `bl_result$scaling`; the model-free exploratory biplot reads it from that `bl_result` too. It never alters the projection, grid, or what the model/`predict_fn` sees -- it is consumed only by the biplot plot methods (see §4.4). Distinct from `X_center`/`X_sd` (the internal PCA standardisation of whatever data was supplied) and the `standardise` flag. A single `method` label applies to all features; per-variable transform families are future work (CLAUDE.md §9).

`bl_apply_scaling(data, bl_result)` is the input-side counterpart: it converts new data given in raw units (e.g. an external applicant) to the model's units, replacing each feature column by `(raw - center) / scale` from the recorded scaling and leaving other columns unchanged. It accepts a `bl_result`, `bl_data` or `bl_filter_result`, and errors when no scaling is recorded, a feature column is missing or non-numeric, or `data` is not a data frame. Any function that takes new data (`bl_select_target()`, `bl_project_points()`, `plot(..., target_point =)`) expects model units.

**`R/outlier_filter.R`**

| Function | Signature | Returns |
|---|---|---|
| `bl_filter_outliers()` | `(bl_data, hull_fraction=0.9, verbose=TRUE)` | `bl_filter_result` |

In the standard workflow, `bl_filter_outliers()` is called internally by `bl_prepare_data()`. Use it directly only when you need to iterate on hull fractions without re-splitting the data (e.g., after `bl_wrap_data()`). Implements the convex hull polygon filter: projects training data to a lightweight 2-PC space, builds a convex hull enclosing `hull_fraction` of the points, and removes observations outside the hull.

**`R/model_fit.R`**

| Function | Signature | Returns |
|---|---|---|
| `bl_fit_model()` | `(train_data, var_names, model_type="GLM", cutoff=0.5, model_params=list())` | `bl_model` |
| `bl_wrap_model()` | `(model, model_type, var_names, predict_fn=NULL, train_data=NULL, cutoff=0.5)` | `bl_model` |

`bl_fit_model()` supports four parsnip/tidymodels types: GLM, SVM, NNET, RForest (the old spelling `"RForrest"` is still accepted with a deprecation warning). All are returned as `workflows::workflow` objects. `bl_wrap_model()` accepts any externally fitted model: GAM (mgcv), GBM (gbm), LDA (MASS), XGB (an `xgb.Booster` from `xgboost::xgb.train()`, or an `xgboost::xgboost()` model fitted on a factor 0/1 response, wrapped as `list(model, features)`; `bl_wrap_model()` stops if an `xgboost()` model is not `binary:logistic` on levels 0/1, since with a numeric response `xgboost()` fits a regression), or any user-defined classifier via `predict_fn`. Use `bl_wrap_model()` for types requiring custom training code, non-default hyperparameters, or not natively supported by `bl_fit_model()`. Both functions store `model_type`, `cutoff`, and `var_names` for consistent downstream use.

**LDA and multi-class prediction (not yet implemented):** Linear Discriminant Analysis naturally extends to k > 2 classes -- its discriminant functions produce one axis per class boundary. The current package is restricted to binary 0/1 outcomes. A future enhancement could expose LDA via `bl_wrap_model()` or a dedicated `bl_fit_lda()` to support multi-class biplots where each class pair yields a separate boundary. See CLAUDE.md Section 9.

### 4.2 Module B — Projection and Biplot Construction
*Instruction manual §3B*

**`R/projection.R`**

| Function | Signature | Returns |
|---|---|---|
| `bl_build_projection()` | `(train_data, var_names, method="PCA", standardise=TRUE, proj_dims=c(1L,2L), bl_model=NULL, cva_classes=NULL, title="")` | `bl_projection` |

Constructs the loading matrix `V` (p × p) and its inverse `tV` (p × p) for either PCA or CVA. For PCA, standardisation is applied by default. **For CVA, `standardise` is forced to `FALSE` internally regardless of the user-supplied value** — biplotEZ handles within-class normalisation internally, making external standardisation incorrect. `V` is the loading matrix `bp$Lmat` from `biplotEZ::PCA()` / `biplotEZ::CVA()`. The `bl_projection` object stores `V`, `tV`, `X_center`, `X_sd`, `method`, `standardise`, `proj_dims`, the biplotEZ S3 object (`biplot_obj`) used for subsequent plotting, `cva_classes`, `point_col`, `train_ranges`, `metric`, `metric_inv`, `metric_type` and `condition_number`. Projected training coordinates are not stored separately; they live in `biplot_obj$Z`, and `bl_build_grid()` recomputes `Z_train` locally. The `biplot_obj` field is the key link between the mathematical projection and the biplotEZ rendering pipeline.

**Design note (Q9):** CVA with only 2 classes is technically a degenerate case but is supported via biplotEZ. This is documented in the function help.

**`R/local_cf.R` — rotation (Phase 3 extension of Module B)**

The private function `.bl_rotate(x_target_st, V, proj_pair)` adapts the `Biplot_rotation()` logic from the research script `1.3 Optimal Rotation.R`. Given a standardised target point and an eigenvector pair, it computes an SVD-based orthogonal rotation matrix `A` such that the rotated loading matrix `Vrho = V %*% t(A)` aligns the target with the chosen projection plane. The SVD construction (`YVr_padded` has non-zero values only in its first two columns) guarantees that the target's information concentrates in columns 1 and 2 of `Vrho` regardless of `proj_pair`. Returns `Vr_rot = Vrho[, c(1, 2)]` (p x 2) and `tVr_rot = tVrho[c(1, 2), ]` (2 x p). Note: `proj_pair` selects which eigenvectors feed into the rotation via `Vr = V[, proj_pair]`, but the *output* columns are always 1-2 of the rotated matrix.

**Caveat (recorded 2026-07-15; behaviour unchanged).** "Aligns the target with the chosen projection plane" above is true of the *target* but not of the *plane*. `Y <- rbind(-x, 0, x)` is rank 1 (its rows are all multiples of `x`), so `M = t(YV) %*% YVr_padded` is rank 1 and its SVD has a `p-1`-dimensional exactly degenerate null space. The Procrustes minimiser is therefore pinned only along the target direction -- the plane's second direction is LAPACK's arbitrary tie-break, and the resulting plane is `span(u1, q)` with `q` not determined by the maths. Measured on the loan data (target 49, pair (2,3); `documentation/biplot-rotation/17_2`, re-measured 2026-10-30): bases differing by 4.65e-15 yield planes 65.91 degrees apart, and only 21% of the plane's second direction (taken orthogonal to the target) lies inside `span(V[,2], V[,3])`. For identical inputs the plane is identical, so results reproduce on one platform; across BLAS/LAPACK builds this is untested. The target lies in the plane regardless, and the counterfactual is still re-scored against the model and so remains a genuine boundary point. This is inherited from the original method, not introduced by the port. See `documentation/biplot-rotation/biplot_rotation_and_pair_selection.md` §4.1 (with Appendix A.1) for the derivation and full measurements, and §5 for a not-yet-implemented deterministic-rotation proposal.

#### 4.2.1 The within-class metric matrix W and Cholesky inversion

`bl_build_projection()` computes and stores a metric matrix `M` and its inverse `M_inv` for use by Phase 2 and Phase 3 distance measures. The matrix is:

- `W` (pooled within-class covariance) when `cva_classes` or `train_data$class` is available -- the standard CVA scatter matrix `W = sum_k (X_k - mu_k)^T (X_k - mu_k) / (n - g)` where `g` is the number of class levels and `mu_k` is the per-class feature mean.
- `Sigma` (total covariance, `cov(X)`) as a fallback when no class information is supplied (rare in this package; `bl_data` almost always has classes).

The metric is the same one CVA itself optimises against: biplotEZ builds the CVA loadings from the same within-class matrix, so `V' W V = I / (n - g)` (biplotEZ uses the sums of squares and products, without the divisor). Storing it makes the projection-to-distance pipeline internally consistent: distances measured in Phase 2 or Phase 3 use the same `W` that defined the biplot axes in Phase 1.

The original source of the within-class metric in the PhD research scripts is `scripts/1 Functions for biplot.R` (research-branch helper), which constructed `Wmat` at the same point as the CVA loading matrix and reused it for per-pair distance comparisons in `1.3 Optimal Rotation.R`. The current package delegates the CVA computation to `biplotEZ::CVA()`, which returns the same matrix as `bp$Wmat` (without the divisor); the package computes `W` itself from the training data and the same class factor, with the divisor `n - g`, and for PCA from the binary class. The constant divisor changes no comparison. See `documentation/boundary-distance-and-robustness.md` Section 1.

**Cholesky decomposition for the inverse.** `W` is symmetric and positive-definite by construction, so it admits a unique factorisation `W = L L^T` where `L` is lower triangular with positive diagonal entries. This is the Cholesky decomposition -- the matrix equivalent of taking a square root. Geometrically, `L^{-1}` is the whitening transform that sends correlated data into an uncorrelated unit-variance frame, so that Euclidean distance in the whitened frame equals Mahalanobis distance under `W` in the original frame.

The package inverts `W` using the idiom `chol2inv(chol(W))` rather than `solve(W)`, for three reasons:

1. **Numerical stability.** Cholesky exploits the symmetric positive-definite structure that `solve()` cannot use; it propagates less round-off error and avoids producing a non-positive `v^T W^{-1} v` (which would silently corrupt distance measures) when `W` is near-singular.
2. **Singularity detection.** `chol()` errors immediately if `W` is not positive-definite -- giving a clean trigger to apply the ridge fallback `W + lambda * I` (with `lambda = 10^-6 * mean(diag(W))`). `solve()` would return a meaningless inverse without warning.
3. **Speed.** `chol2inv()` is roughly 2x faster than `solve()` for SPD matrices; not the primary reason but a free benefit.

The `chol(W)` factor itself is not retained -- only `W` (as `metric`) and `W^{-1}` (as `metric_inv`) are stored on `bl_projection` (and propagated to `bl_result`). The Cholesky step is purely an internal numerical detail of the inversion. Downstream code multiplies vectors by `metric_inv` directly.

**Singular-W safeguard.** When `n - g < p` (more features than effective sample size after class adjustment), `W` is rank-deficient and Cholesky fails. The package applies a ridge-regularised fallback `chol2inv(chol(W + lambda * I))` so the distance measures remain well-defined. The `metric_type` attribute is unchanged; the regularisation is transparent to the user.

The helper that performs this computation is the private `.compute_metric_inverse()` in `R/projection.R`. The three fields it produces (`metric`, `metric_inv`, `metric_type`) are stored on `bl_projection` and propagated through `bl_assemble()` into `bl_result`.

### 4.3 Module C — Grid Construction and Boundary Approximation
*Instruction manual §3C*

**`R/biplot_grid.R`**

| Function | Signature | Returns |
|---|---|---|
| `bl_build_grid()` | `(train_data, bl_projection, bl_model, m=200L, cutoff=bl_model$cutoff, b_margin=0.001, polygon=NULL, outlie=1, calc_hull=TRUE)` | `bl_grid` |

Builds an `m × m` regular grid over the Z-space, back-projects each grid point to X-space using `tV`, scores it through the model, and extracts contour lines at `cutoff ± b_margin` using `grDevices::contourLines`. `cutoff` defaults to `bl_model$cutoff` (0.5 unless the model was built with another value), so the grid's contours sit at the same threshold that `bl_find_boundary()`, `bl_surrogate()` and `bl_find_local_cf()` read from `bl_result$cutoff`. Scores in chunks of 50,000 for memory safety. Stores:

- `ct` — full contour list (for plotting and global CF search)
- `ct_surrogate` — hull-clipped contours (for surrogate model only)
- `col_value` — per-grid-point colour vector (blue→white→red by probability)
- `polygon` — the Z-space convex hull as a `SpatialPolygons` object
- `hull_fraction` — the `outlie` value used
- `cutoff` — the decision threshold the contours were extracted around

Only the `calc_hull` trimming of the prediction surface is visual: with `calc_hull = TRUE` (the default) the stored `Zgrid`, `Xgrid`, `grid_prob` and `col_value` keep just the grid points inside the hull. The polygon itself is not visual-only: `bl_find_boundary()` clips contours to it, and `bl_surrogate()` uses it. The `bl_surrogate()` function reads `ct_surrogate` directly; user code never needs to distinguish the two.

### 4.4 Phase 1 Assembly and Plotting

**`R/result.R`**

| Function | Signature | Returns |
|---|---|---|
| `bl_assemble()` | `(bl_data, bl_model=NULL, bl_projection, bl_grid=NULL)` | `bl_result` |
| `bl_build_result()` | `(bl_data=NULL, bl_model=NULL, method="PCA", proj_dims=c(1L,2L), standardise=TRUE, cva_classes=NULL, title="", m=200L, outlie=1, calc_hull=TRUE, b_margin=0.001)` | `bl_result` |

The central Phase 1 anchor object. Consolidates all metadata into a single reproducible object: training/test data, model, projection matrices (`V`, `tV`), centring/scaling (`X_center`, `X_sd`), grid and contours, polygon, `train_ranges`, `var_names`, `proj_dims`, `cutoff`, `b_margin`, and (when set via `bl_set_scaling()`) the display-only `scaling` list. The `biplot_obj` from `bl_projection` is carried forward for plotting.

`bl_assemble()` accepts either a `bl_filter_result` (from `bl_prepare_data()` / `bl_filter_outliers()`) or a `bl_data` (from `bl_wrap_data()`) as `bl_data`; there is no separate filter argument. It stops if `bl_grid$cutoff` differs from `bl_model$cutoff`, so the grid's contours and every downstream function use one threshold; a `bl_grid` built before the `cutoff` field existed has none and skips the check.

**`bl_build_result()` without a model:** When `bl_model = NULL`, the grid step is skipped and `bl_assemble()` returns a model-free `bl_result` (no grid or contours; `model`, `cutoff` and `biplot_grid` are `NULL`). `plot_biplotEZ()` then colours the points by true class. This allows projection-only exploration before a model is fitted.

**`R/plot_biplot.R`**

| Function | Signature | Returns |
|---|---|---|
| `plot_biplotEZ()` | `(bl_result, points=NULL, target_point=NULL, target_label=NULL, no_grid=FALSE, plot_points=TRUE, confusion_cols=TRUE, no_contour=FALSE, new_title=NA, cex_z=0.5, label_dir="Paral", label_cex=1, tick_label_cex=0.6, ticks_v=1L, ticks_var=0L, ticks_n=5L, which=NULL, X_names=NULL, label_offset_var=0L, label_offset_dist=1.5, rotate_deg=0, grid_col=NULL, contour_col="black", contour_lwd=1.5, contour_lty=1L)` | `bl_result` (invisible) |

Seven-step rendering pipeline using biplotEZ:

1. **Base axes** — biplotEZ renders the axis skeleton (invisible samples, `opacity=0`)
2. **Prediction grid** — coloured squares per grid point
3. **Data points** — confusion-coloured (TP=red, TN=blue, FP=purple, FN=orange) or prediction-coloured for unlabelled data
4. **Axes redrawn on top** — so variable axes are visible over the grid
5. **Contour lines** — decision boundary approximation
6. **Target** — optional highlighted observation (yellow circle)
7. **Prediction summary** — printed to console (accuracy if labels known, class split if not)

`plot_biplotEZ()` draws no boundary arrows. Observation-to-counterfactual arrows are drawn per click by `bl_pick_point(bl_result, data = ..., bl_boundary = bl_bnd)` (§4.10).

The `rotate_deg` parameter patches the biplotEZ object's `Z`, `Lmat`, and `ax.one.unit` fields to rotate all rendered elements without rerunning the projection pipeline. **`rotate_deg` is only for viewing the global biplot** (`plot_biplotEZ()`, `plot.bl_surrogate()`). Whenever the rotation function `.bl_rotate()` is used -- the local biplot for an individual target, `plot.bl_local_result()` and `plot.bl_sparse_result()` -- the plot is not turned further: `rotate_deg` is in effect always 0 there. Those two functions have no `rotate_deg` argument and stop if one is passed, because the local biplot's orientation is fixed by the optimal rotation, which is part of the method. `rotate_deg` is never used to plot a rotated individual point. The optional `grid_col` parameter overrides the blue-white-red gradient with a hard binary two-colour scheme.

#### 4.4.1 Raw-unit axis relabel (`.bl_rescale_biplot_axes()`)

When `bl_result$scaling` is present (set via `bl_set_scaling()`), each biplot plot method relabels its axes into the original feature units via the private helper `.bl_rescale_biplot_axes(biplot_obj, scaling, var_names)`, called after any rotation and `new_title` override and before the first `plot()`.

Mechanism: biplotEZ computes axis tick *labels* in `.calibrate.axis()` as an affine map of the object's `$means` and `$sd` -- `label = means + sd * axis.vals` -- with the nice tick values drawn from `pretty(range(Xhat))`, where `Xhat` is reconstructed from `$means`/`$sd`/`$scaled`/`$center`. The 2D geometry (`$Z`, `$Lmat`, `$ax.one.unit`, `$e.vects`) is independent of these fields, and a data point's displacement along an axis (`axis.vals`) is fixed by geometry alone. So for a user pre-standardisation `std = (raw - center) / scale`, setting

    means_new = means * scale + center
    sd_new    = sd * scale
    $scaled <- TRUE ; $center <- TRUE   (geometry fields untouched)

makes every label read `label_new = label_old * scale + center = raw` and reconstructs `Xhat` on the raw range, while plotted positions stay byte-identical. This holds uniformly for PCA (`scaled` TRUE -> `sd` = column SDs; `scaled` FALSE -> `sd` = 1) and CVA (`scaled` FALSE, so `sd_new = scale` supplies the `d(raw)/d(std)` factor that `ax.one.unit` -- built for unit `std` -- otherwise lacks). The helper is a no-op when `scaling` is `NULL` (back-compatible with older `bl_result` objects) and warns, leaving axes in standardised units, if the scaling does not cover every biplot feature. Wired into `plot_biplotEZ()`, `plot.bl_projection()`, `plot.bl_local_result()` (applied to the SVD-rotated object -- `$means`/`$sd` are rotation-invariant), `plot.bl_surrogate()`, and `plot.bl_sparse_result()` (via pass-through to the local plot). Verified by a round-trip test asserting raw-unit labels and geometry invariance for PCA (`standardise = TRUE`) and CVA. Printed feature values (observed, counterfactual, sparse, target) are converted to raw units at display time by `.scale_to_raw()` in `print.bl_target()`, `print.bl_counterfactual()`, `print.bl_shapley()` and `print.bl_sparse_result()` (see §4.9). Distances (`dist_z`, `dist_mahalanobis`, `plot.bl_boundary()`, `bl_robustness()`) and Shapley contributions stay in model units.

**`R/project_points.R`**

| Function | Signature | Returns |
|---|---|---|
| `bl_project_points()` | `(data, bl_result, filter_to_polygon=FALSE, filter_to_train_ranges=FALSE)` | `bl_points` |
| `bl_predict()` | `(bl_result, data=NULL)` | `data.frame` |

`bl_project_points()` projects any data frame (train, test, external) into Z-space and scores it through the model. Returns a `bl_points` object suitable for passing to `plot_biplotEZ()` via the `points` parameter. `bl_predict()` wraps `bl_project_points()` and returns a tidy data frame with columns `row`, `pred_prob`, `pred_class`, `true_class` (if known), `confusion` (TP/TN/FP/FN if known), and all feature columns — intended for inspection and target selection in interactive scripts.

### 4.5 Module D (Global) — Global Counterfactual Search
*Instruction manual §3D*

**`R/boundary.R`**

| Function | Signature | Returns |
|---|---|---|
| `bl_find_boundary()` | `(bl_result, data=NULL, tdp=NULL)` | `bl_boundary` |

Searches for the nearest decision boundary point for each observation in `data`. For each observation, iterates over all contour segments in `bl_grid$ct`, clips segments to the training hull polygon, then finds the nearest contour point using a block-wise nearest-neighbour search (`.nearest_idx_block()`). The helper takes the exact nearest vertex with `max.col(-d2, ties.method = "first")`, the first one on an exact tie, and uses no random numbers. `bl_find_boundary()`, `bl_surrogate()` and `bl_find_local_cf()` all share it, so their results do not depend on the session's RNG state or on earlier calls. R's default, `ties.method = "random"`, treated every vertex within 1e-5 of the farthest vertex's squared distance as tied and drew one at random; that default was inherited from the PhD code and replaced on 2026-10-30 (`documentation/nearest-vertex-tie-break.md`). Stores `Z_obs`, `B_z`, `B_x`, `B_pred`, and `dist_z` per observation.

**Feasibility filtering — post-selection:** `train_ranges` are applied **after** selecting the geometrically nearest boundary point, not as a pre-filter on contour segments. This preserves geometric correctness: the nearest point on the decision boundary is found first, then checked for feasibility. Out-of-range counterfactuals are kept; the function prints a console message with their count (there is no per-row flag in the returned object). The Z-space hull polygon is applied as a pre-filter (contours are clipped before search).

### 4.6 Module E — Distance and Robustness Analysis
*Instruction manual §3E*

**`R/boundary_plot.R`**

| Function | Signature | Returns |
|---|---|---|
| `plot.bl_boundary()` | `(x, type=c("jitter","boxplot"), distance=c("mahalanobis","euclidean"), ...)` | list (invisible) |
| `bl_robustness()` | `(bl_boundary, distance=c("mahalanobis","euclidean"))` | list |

`plot.bl_boundary()` visualises the per-variable distance from each observation to its boundary counterfactual, using ggplot2 jitter or boxplot. Points are coloured by confusion type (TP/TN/FP/FN). `bl_robustness()` returns a per-variable distance summary and a scalar total robustness score.

**Per-feature standardisation denominator (`distance` parameter):**

| Value | Denominator | Interpretation |
|---|---|---|
| `"mahalanobis"` (default) | `sqrt(diag(W))` from `bl_result$metric` | Within-class SD per feature. Features that are good class separators (large between-class variance, small within-class variance) are correctly amplified in the importance measure. |
| `"euclidean"` | `X_sd` (total-SD alternative) | Total SD per feature. Conflates within- and between-class variance. |

When `distance = "mahalanobis"`, `plot.bl_boundary()` prints a Mahalanobis check, summed across observations: the squared length of the plotted per-feature distances, `sum_j v_j^2 / W_jj` = `sum(vec_to_boundary_sd^2)`, against the full squared Mahalanobis distance `v' W^-1 v`, with their difference as a percentage of the full. The difference is what the per-feature plot leaves out by ignoring the correlations in W: positive means the plot understates the distance, negative that it overstates it. An absolute difference of 25% or more triggers a note pointing to Section 4.6.1 for theoretical alternatives. The four numbers are returned as `mahalanobis_check` (`plotted`, `full`, `difference`, `pct`; `NULL` for `"euclidean"`). Before 2026-10-31 the "diagonal" used `diag(W^-1)`, which is not the plotted measure (see `documentation/boundary-distance-and-robustness.md` §4.2).

#### 4.6.1 Shapley attribution: theoretical correctness vs. computational cost

The per-variable importance measure produced by `bl_robustness()` and `plot.bl_boundary()` uses the *diagonal* of the within-class covariance matrix `W` to standardise per-feature distances to the boundary. This diagonal approximation preserves a clean per-feature interpretation but ignores cross-feature correlations encoded in the off-diagonal of `W^{-1}`.

The **theoretically correct** decomposition of the full squared Mahalanobis distance `d_M^2(v) = v^T W^{-1} v` into per-feature contributions is the **Shapley value attribution** from cooperative game theory: treat the p features as players and `d_M^2` as the value function, then compute each feature's Shapley value as its average marginal contribution across all `2^p` subsets. The resulting per-feature attributions `phi_j` satisfy the efficiency axiom `sum_j phi_j = d_M^2(v)`, distribute the cross-correlation structure of `W^{-1}` across features in a uniquely fair way, and respect linearity, symmetry, and null-player axioms.

This was identified in the PhD research as the methodologically correct per-feature attribution. It is **not implemented in the package** because the computational cost is prohibitive for the global Phase 2 use case: exact Shapley requires `2^p` subset evaluations per observation, and Phase 2 distance-to-boundary measures aggregate across all training/test observations -- so the total cost is `O(n * 2^p)` model evaluations. For the loan example in the development harness (`n` = 15,970 training observations after the hull filter, `p = 9` before pruning), this is `n * 2^9` ~ 8.2 million model scorings just to build the importance plot. For larger feature sets (`p > 14`) the cost becomes infeasible even with the permutation approximation used elsewhere in the package (`R/shapley.R`).

The diagonal approximation was chosen instead as a deliberate trade-off: linear cost (`O(n)` model evaluations), preserved per-variable interpretation, and the main methodological correction (within-class noise instead of total variance) achieved without the combinatorial expense. A Mahalanobis check (printed by `plot.bl_boundary()` when `distance = "mahalanobis"`) reports how far the plotted per-feature measure, `sum_j v_j^2 / W_jj`, falls short of or exceeds the full `d_M^2` -- giving users a direct measure of how much information is foregone for their specific data. Where this fraction is small, the diagonal approximation is essentially lossless and the cost saving is "free".

Phase 3 (`bl_shapley`) does use the exact Shapley formulation, but only for a single observation at a time -- the cost is `2^p` rather than `n * 2^p`, which is tractable for the local interpretation use case.

### 4.8 Module D (Local) — Local Counterfactual Search
*Instruction manual §3D, §3B (rotation)*

**`R/local_cf.R`**

| Function | Signature | Returns |
|---|---|---|
| `bl_select_target()` | `(bl_result, target, data=NULL)` | `bl_target` |
| `set_filters()` | `(bl_target, ...)` | `bl_filters` |
| `bl_find_local_cf()` | `(bl_result, bl_target, set_filters=NULL, max_pairs=21L, m=200L, distance=c("mahalanobis","euclidean"), verbose=TRUE)` | `bl_local_result` |

**`bl_select_target()`** wraps a single observation (integer row index or single-row data frame) into a `bl_target` object, projecting it into Z-space and scoring it through the model. External data frames (no class column, not in train/test) are fully supported. A data-frame target must be in model units; the private `.warn_target_range()` warns when any of its features lies outside `train_ranges` and, when a scaling is recorded and converting the target would bring more features into range, suggests `bl_apply_scaling()` (the target looks like raw units). Index targets are not checked.

`bl_target` fields: `x_obs` (one-row data frame of features), `z_obs` (1 x 2 Z-space coordinates), `pred_prob`, `pred_class` (at `cutoff`), `row_id` (row index into `data`, or `NA` for a data-frame target), `class_obs` (true class, or `NA`), and `scaling` (display-only raw-unit scaling, or `NULL`). `class_obs` is resolved at selection time from the same one-row source that supplies `x_obs`: `data[row_id, ]` for an index (any data frame, not only `test_data`), or the `target` frame itself. It reads the `class` column when present, otherwise the first non-feature column; with no such column, or a non-numeric label, it is `NA`. `plot.bl_local_result()` colours the target by confusion group (TP/TN/FP/FN) from `class_obs` against `pred_class`, and by `pred_class` alone when `class_obs` is `NA` or absent (objects built before the field existed).

**`set_filters()`** defines per-variable actionability constraints for the local search:

| Constraint | Meaning during search | Meaning in sparse CF |
|---|---|---|
| `"decrease"` | CF value must be ≤ observed | Not special — Shapley decides |
| `"increase"` | CF value must be ≥ observed | Not special — Shapley decides |
| `"fixed"` | CF value within ±0.5 of observed (model units); after the search, restored to observed when the restored point still crosses the boundary | Always reverts to observed value |
| `c(min, max)` | CF value must lie in `[min, max]` | Not special — Shapley decides |

**`bl_find_local_cf()`** iterates over up to `max_pairs` eigenvector pairs in canonical order — (1,2), (1,3), (2,3), (1,4), … — testing a maximum of 21 combinations by default, which is every pair for up to 7 features (configurable). For each pair:

1. Rotates the biplot via `.bl_rotate()` to align the target with the projection plane
2. Projects the target and all training observations into the rotated Z-space
3. Builds an `m × m` grid, scores through the model (chunked for memory)
4. Extracts contour lines at `cutoff ± b_margin`
5. Back-projects contour segments to X-space
6. Filters contour vertices through a four-stage cascade:
   a. Opposing-class contour level only (cheap, pre-back-projection).
   b. **`set_filters` actionability first** (when supplied) -- the
      "fixed", "decrease", "increase", `c(min,max)` constraints. Often
      the most selective filter; running it first with an early-exit
      check on `any(keep)` short-circuits the rest of the cascade on
      vertices it rejects.
   c. **`train_ranges` feasibility second** -- per-feature [min, max]
      bounds from training data, applied only to vertices that
      survived (b).
   d. **Model-consistency re-scoring** -- the surviving vertices are
      passed back through `.pred_function()` and dropped if the model's
      actual probability disagrees with the contour level's side of
      `cutoff`. This is the most expensive stage; the ordering of
      (b)-(c) is chosen so it sees the smallest possible set.
7. Finds the nearest valid boundary point among the survivors of (d).

**Cross-pair selection metric (`distance` parameter):**

| Value | Selector | Notes |
|---|---|---|
| `"mahalanobis"` (default) | Squared Mahalanobis distance in X-space: `d_M^2 = (B_x - x_obs)^T W^{-1} (B_x - x_obs)` using `bl_result$metric_inv` | The PhD's cross-pair criterion (`pc.distz <- v %*% Wmat_inv %*% t(v)`). Under PCA it uses the binary-class `W`, which is a package choice; the thesis's PCA rule is Euclidean. |
| `"euclidean"` | Z-space Euclidean: `sqrt(sum((Z_target - B_z)^2))` | Under PCA, standardised Euclidean distance: the thesis's PCA rule. |

**Under CVA the two selectors are identical.** The CVA loadings satisfy `V'WV = I/(n-g)`, and every rotated basis inherits it, so for the search's in-plane point `d_M^2 = (n-g) * dist_z^2` for every pair: 15992 for every pair on the loan harness. Under PCA they are different metrics and can pick different pairs. See `documentation/biplot-rotation/biplot_rotation_and_pair_selection.md` §3.4.

Within-pair selection (the nearest valid contour vertex) always uses 2D Euclidean distance; only the cross-pair comparison is governed by `distance`. The `bl_local_result` object reports both `dist_z` and `dist_mahalanobis` for the winning pair, plus `all_distances` and `all_distances_mahalanobis` per pair tried.

The pair producing the globally minimum value of the chosen selector is selected. The result stores the full grid, contours, rotation matrices (`Vr_rot`, `tVr_rot`), and the `set_filters` object (needed by `bl_find_sparse_cf()`).

**Fixed-feature restore (post-selection, private `.restore_fixed()`).** The search accepts a `"fixed"` feature within `.fixed_tol` = 0.5 model units of its observed value, because a vertex of the 2D boundary contour rarely holds a feature at exactly its observed value. After the best pair is chosen, every fixed feature the search moved is set back to its observed value and the point is re-scored. If the restored point still crosses the boundary (predicted class differs from the target's) and lies within `train_ranges`, it replaces `B_x` and `B_pred`, and `B_z` becomes its projection `((B_x - X_center) / sv) %*% Vr_rot`. Otherwise the search's point is kept. The new field `fixed_check` (`NULL` when no fixed feature moved) records `vars`, `applied`, `pred_restored`, `in_range` and `search_point` (the search's `B_x`, `B_z`, `B_pred`). `dist_z`, `dist_mahalanobis` and the per-pair tables stay the search's values, because they describe the pair choice; `bl_counterfactual` is built from the selected point. See `documentation/fixed-constraint-restore.md`.

**`bl_counterfactual` companion object.** Alongside `bl_target` (the observed point), the result carries `bl_local$bl_counterfactual` -- a `"bl_counterfactual"` S3 object that mirrors `bl_target` and packages the boundary point found by the search (built by private `.make_bl_counterfactual()`; `NULL` when no solution). Fields: `x_cf` (1-row data frame `B_x`, model units), `z_cf` (`B_z`), `pred_prob` (`B_pred`), `pred_class` (`as.integer(B_pred >= cutoff)`), and `scaling`. Its `print.bl_counterfactual()` method displays the feature values in original (raw) units when a scaling was recorded via `bl_set_scaling()` -- using `.scale_to_raw(..., kind = "level")` -- exactly like `print.bl_target()`; storage stays in model units. `print.bl_local_result()` prints, in order: the search summary (plus `Fixed restored : <vars>` when a restore was applied), the Target and Counterfactual blocks, the per-pair distances, and finally an observed / counterfactual / change / constraint table (one row per feature, `var_names` order, raw units when scaled) built by the private `.cf_compare_table()`. When the search moved a `"fixed"` feature, a note under the table (private `.fixed_notes()`) gives the move, the tolerance in display units, and whether the restored point was used. **Number format:** `.cf_compare_table()` returns the table unrounded plus `digits`, the decimals per feature row: 2, or more (up to 4, two significant digits) where a difference from the observed value would print as 0.00 (private `.fmt_digits()`). `.format_cf_table()` turns the numeric columns into fixed-notation strings with `.fmt_fixed()` (never scientific notation, never `-0.00`). `print.bl_local_result()` passes the same `digits` to `print.bl_target()` and `print.bl_counterfactual()` (both gain `digits = NULL`; by default each value gets `.fmt_digits()`), so the three blocks agree.

**Important constraint difference from global search:**

| Constraint | Global (`bl_find_boundary`) | Local (`bl_find_local_cf`) |
|---|---|---|
| Z-space hull polygon | Applied | **Not applied** — rotation invalidates it |
| `train_ranges` | Reported only (post-selection, no exclusion) | Applied as hard in-loop filter |
| Actionability filters | Not available | Applied via `set_filters` |

**Why Filter (d) is not batched across segments.** The model re-scoring inside the per-pair loop is the dominant computational cost, and a meaningful wall-clock saving is available by collecting all surviving vertices across all opposing-class segments and scoring them in a single `.pred_function()` call (especially for XGBoost, where each call has DMatrix-construction overhead). The current per-segment call is retained deliberately: the bookkeeping required to split a batched prediction back to its source segments adds complexity that obscures the search logic, and the per-pair cost is already small enough (typically sub-second on a 100x100 grid) that the saving doesn't justify the trade. If a future use case pushes `m` high enough that this dominates, the batch is the right next optimisation; the segment loop is structured to make that refactor local.

**`train_ranges` enforcement asymmetry between global and local search.** On the **default global path** (`bl_find_boundary()` followed by `bl_project_points(..., filter_to_train_ranges = FALSE)`), `train_ranges` is never used to exclude points. `bl_find_boundary()` only reports out-of-range counterfactuals as a console message (its post-selection feasibility check) -- it does not discard them, because doing so would select a geometrically incorrect (farther) boundary point. `bl_project_points()` enforces `train_ranges` only when the caller opts in via `filter_to_train_ranges = TRUE`. The local search, by contrast, applies it as a hard in-loop filter (per the cascade above) -- not because feasibility matters more in Phase 3, but because the SVD rotation invalidates the Z-space hull polygon and `train_ranges` is the only feasibility constraint that survives the rotation. If a future requirement asks the global search to enforce actionability and feasibility (e.g. to surface only realistic counterfactuals in `bl_find_boundary()` rather than reporting them post-hoc), the local cascade above is the template -- introduce a `set_filters` argument and the four-stage cascade into the segment loop of `bl_find_boundary()`.

**`plot.bl_local_result()`** renders using the same biplotEZ pipeline as `plot_biplotEZ()`. The biplotEZ object from `bl_result` is patched in-place with the rotated local coordinates before rendering:

```r
biplot_plot$Z[, proj_dims]    <- Z_train_rot   # rotated training coordinates
biplot_plot$Lmat[, proj_dims] <- Vr_rot         # rotated loading matrix
biplot_plot$ax.one.unit       <- (1 / diag(t(tVr_rot) %*% tVr_rot)) * t(tVr_rot)
```

This formula for `ax.one.unit` is identical to the `rotate_deg` path in `plot_biplotEZ()`. The target point is coloured by the confusion scheme (TP/TN/FP/FN) from `bl_target$class_obs` against `bl_target$pred_class`; when `class_obs` is `NA` (no class column) it is red (predicted 1) or blue (predicted 0). Parameters shared with `plot_biplotEZ()`: `no_grid`, `plot_points` (default `FALSE` here, `TRUE` there), `no_contour`, `cex_z`, `label_dir`, `label_cex`, `tick_label_cex`, `ticks_v`/`ticks_var`/`ticks_n`, `which`, `X_names`, `label_offset_var`/`label_offset_dist`, `contour_col`/`contour_lwd`/`contour_lty`, `new_title`. Local-only: `show_arrows`, `arrow_col`, `print_summary`. `plot_biplotEZ()`-only: `points`, `target_point`, `target_label`, `confusion_cols`, `grid_col`, `rotate_deg`. **`plot.bl_local_result()` has no `rotate_deg`:** the local biplot keeps the orientation set by the optimal rotation `.bl_rotate()`, and passing `rotate_deg` stops with an error before any device opens (without the check it would fall into `...` and be silently ignored). `plot.bl_sparse_result()` forwards `...` to it and so refuses `rotate_deg` the same way; its sparse-CF cross is projected with `Vr_rot`, the same frame as the rest of the local plot. `rotate_deg` is only for viewing the global biplot (§4.4).

### 4.9 Module G — Shapley Values and Sparse Counterfactual
*Instruction manual §3G*

**`R/shapley.R`**

| Function | Signature | Returns |
|---|---|---|
| `bl_shapley()` | `(bl_local_result, exact_max_vars=14L, approx_perm=2048L, seed=NULL)` | `bl_shapley` |
| `bl_find_sparse_cf()` | `(bl_shapley_result, round_to=NULL)` | `bl_sparse_result` |

**`bl_shapley()`** computes Shapley values for the path from the observed point to the boundary counterfactual. Two computation paths:

- **Exact** (`p ≤ exact_max_vars`, default 14): evaluates all 2^p subsets using the weighted marginal contribution formula, adapted from research script `1.2 Run_Shapley_optimized.R`.
- **Permutation** (`p > exact_max_vars`): samples `approx_perm` random permutations and averages marginal contributions. Only this path uses `seed` (`NULL` by default, so repeated calls give independent estimates; an integer calls `set.seed()`). The exact path is deterministic.

Variables are classified as `"Supports"` or `"Contradicts"` using the following logic from research script `4.4 Local Interpretation Shapley.R`:

```r
either class:         |Shapley| < 1e-8 → No effect   (checked first)
class 0 observation:  positive Shapley → Supports,  negative → Contradicts
class 1 observation:  negative Shapley → Supports,  positive → Contradicts
```

The `"No effect"` class (added 2026-10-29) departs from the research script, which counted a zero value as `"Supports"` for a class-0 target. A Shapley value of exactly 0 means the feature's change never moves the prediction, for example a small change that crosses no split of a tree model. The class keeps such a feature out of the sparse counterfactual. See `documentation/sparse-counterfactual.md` §1.

`print.bl_shapley()` shows the predictions (observed, full CF), the Shapley sum, and a table in the same layout as `print.bl_local_result()` (shared builder `.cf_compare_table()`, rows in `var_names` order): `observed`, `counterfactual`, `change`, `constraint`, plus `shapley` (prediction units, not converted; 2 decimals, or more where a non-negligible value would print as 0.00) and `contribute`. `plot.bl_shapley()` renders a ggplot2 horizontal bar chart (darkblue = Supports, grey70 = Contradicts) with y-axis labels `"variable: observed → change_to_boundary"` in model units; rows are sorted by signed Shapley value (ascending for a class-0 target, descending for class 1).

**Raw-unit feature-value display (when `bl_result$scaling` is set via `bl_set_scaling()`).** The observed and counterfactual feature values shown by `plot.bl_shapley()`, `print.bl_shapley()`, `print.bl_sparse_result()`, `print.bl_target()`, `print.bl_counterfactual()` and `print.bl_local_result()` are converted back to original units at display time by the private helper `.scale_to_raw(values, scaling, var_names, kind)` (`R/data_prepare.R`). The two conversion kinds matter: a **level** (observed value, full CF `B_x`, sparse CF, counterfactual end) maps as `value * scale + center`, whereas a **delta** (`data_to_boundary = end - start`) maps as `value * scale` with no centre term (a difference is translation-free). When scaling is present the `plot.bl_shapley()` y-axis label switches from `observed → change` to `observed → counterfactual` in raw units (counterfactual = `pred_data + data_to_boundary`, converted as a level). `bl_select_target()` stores `scaling` on the `bl_target` so `print.bl_target()` (and `print.bl_local_result()`, which delegates to it) can convert. Conversion is display-only -- the stored `shapley_df` / `x_sparse` / `x_obs` remain in model units. The Shapley *contributions* (`shapley_cause`) are in prediction-impact units, not feature units, and are deliberately left unconverted. No-op (and warns on incomplete scaling) when `scaling` is absent. See Section 4.4.1 for the axis-relabel counterpart.

**`bl_find_sparse_cf()`** builds a sparse version of the counterfactual by greedy selection (since 2026-10-29; previously every `"Supports"` variable was changed at once):

1. Candidates: `"Supports"` variables that are not `"fixed"` in `set_filters`, ordered by absolute Shapley value, largest first. `"Contradicts"`, `"No effect"`, `"Unknown"` and fixed variables never change.
2. Start from the observed point. Change one candidate at a time to its CF value (optionally rounded by resolution `round_to`), re-score through the model, and record the step in `sparse_path`.
3. Stop at the first point whose predicted class differs from the target's. If no step crosses, every candidate has been changed.
4. Set `solution_valid = TRUE` if the final point's predicted class flips
5. Annotate `shapley_df` with `used_in_sparse` (`TRUE` for the variables on the greedy path) and `x_sparse_val`

Re-scoring, rather than summing Shapley values, uses the model's actual prediction at each partial counterfactual (a Shapley value is an average over coalitions, not the effect when added first), at most `p` model calls. The selection follows the Shapley order, so it is not guaranteed minimal. New field `sparse_path`: `step`, `variable`, `shapley`, `pred`, `crosses`. See `documentation/sparse-counterfactual.md` §2.

The `round_to` parameter is **resolution-based** (round to nearest multiple), not decimal places:
- `round_to = 0.5` → rounds to nearest 0.5
- `round_to = 1` → rounds to nearest integer
- `round_to = NULL` (default) → no rounding

Rounding acts on the stored model-unit values (z-scores for a standardised model), uses the nearest multiple, and does not re-check constraints. Its issues and possible changes are recorded, for future investigation, in `documentation/sparse-counterfactual.md` §3.

`print.bl_sparse_result()` shows three predictions — Observed, Full CF, Sparse CF — to allow verification of the classification change at each stage, then a table in the same layout as `print.bl_local_result()` (shared builder `.cf_compare_table()`): one row per feature with `observed`, `counterfactual` (full CF), `sparse`, `change` (sparse minus observed), `constraint` and `used` (`used_in_sparse`), followed by the greedy path (`sparse_path`; its `pred` keeps up to 4 decimals within 0.005 of the cutoff, so the side of the boundary is visible). `plot.bl_sparse_result()` renders the full local biplot with both CFs overlaid: grey cross = full CF, green = sparse CF valid, yellow = sparse CF invalid.

### `R/utils.R`
Input validation functions used by all exported functions: `stop_if_not_data_frame()`, `stop_if_not_character()`, `stop_if_col_missing()`, `stop_if_not_in_range()`, `stop_if_not_positive_integer()`, `stop_if_not_scalar_numeric()`. Also `calc_gini()` (2 × AUC − 1) used for per-iteration accuracy reporting in the outlier filter.

### `R/hull_utils.R`
`.build_hull_polygon()` — constructs a convex hull `SpatialPolygons` object from the Z-space training coordinates. `outlie` is passed to `aplpack::plothulls(fraction = )`: the fraction of points the hull encloses (`1` = all). Uses `aplpack::plothulls()` for the hull computation and `sp::SpatialPolygons` for the polygon object. `plothulls()` computes by drawing, so the helper draws on a temporary off-screen `png()`, closes only that device, and re-activates the caller's device; `.bl_get_plot_bounds()` (`R/biplot_grid.R`) handles its off-screen render the same way. `.poly_clip()` clips a matrix of Z-space points to the interior of the polygon. `.points_in_polygon()` returns a logical membership vector.

**Note:** `.poly_clip()` is also defined locally inside `boundary.R` (code duplication). The authoritative definition is in `hull_utils.R`; the copy in `boundary.R` is a known technical debt item to remove in a future refactor.

### `R/feasibility_utils.R`
`get_variable_ranges()` extracts per-variable min/max bounds from training data as a named list of `c(min, max)` values. `get_filter_logical_vector()` evaluates these row-wise against any data frame — used in both global and local CF search to enforce `train_ranges`.

### `R/model_utils.R`
`.fit_model()` dispatches to the appropriate parsnip/tidymodels fitting backend by `model_type`: GLM, SVM (kernlab), NNET, RForest (rpart). All return a fitted `workflows::workflow`. Types not supported here (GBM, GAM, LDA, XGB) must be fitted externally and registered via `bl_wrap_model()`.

### `R/predict_utils.R`
`.pred_function()` is the single unified prediction interface used by all boundary, surrogate, and Shapley functions. Dispatches to: tidymodels `predict(type = "prob")` for `bl_fit_model()` workflows; the raw-model paths for `bl_wrap_model()` objects (GLM/GAM `predict(type = "response")`, GBM `predict.gbm()`, LDA posterior, `e1071` SVM probability extraction, NNET, RForest, XGB via `xgb.DMatrix` for an `xgb.train()` booster or via the data frame for an `xgboost()` model, whose predict method refuses an `xgb.DMatrix`); or a user-supplied `predict_fn`. Returns a numeric probability vector, floor-rounded to 3 decimal places: `floor(x * 1000) / 1000`. It does not clamp; only `bl_build_grid()` clamps grid probabilities to [0, 1]. The `b_margin` parameter stored in `bl_result` controls the contour band half-width and is independent of the prediction precision applied here.

## 6. Design Decisions and Manual Mapping

### 6.1 Two-phase workflow (Manual §4, Architecture Q2–Q3)

The manual specifies a two-phase workflow. This is implemented as:

- **Phase 1** (`bl_prepare_data` [includes `bl_filter_outliers`] → `bl_fit_model/bl_wrap_model` → `bl_build_projection` → `bl_build_grid` → `bl_assemble`): produces `bl_result`, the anchor object for all downstream analysis. All Phase 1 choices (model, projection, grid resolution, polygon) are fixed at assembly. For the external-data path, replace `bl_prepare_data` with `bl_wrap_data` (no hull filtering).
- **Phase 2 global** (`bl_find_boundary`, `bl_robustness`, `bl_surrogate`): operates on datasets, produces per-observation summaries.
- **Phase 2 local / Phase 3** (`bl_select_target`, `set_filters`, `bl_find_local_cf`, `bl_shapley`, `bl_find_sparse_cf`): operates on single observations.

### 6.2 biplotEZ dependency (Architecture Q4)

biplotEZ computes the PCA/CVA loading matrix (`V = bp$Lmat` from `biplotEZ::PCA()` / `biplotEZ::CVA()`), supplies the plot bounds (via an off-screen render, `.bl_get_plot_bounds()`), and draws the axis skeleton. Grid scoring, contour extraction, inverse projection, counterfactual search and Shapley computation are performed without it. The plotting pipeline uses biplotEZ only to draw the axis skeleton (`samples(opacity=0)` + `axes()`), then overlays grid, points, contours, and markers manually using `graphics::points()` and `graphics::lines()`. This decoupling limits the computation pipeline's exposure to biplotEZ API changes to the projection step and the bounds render.

### 6.3 CVA with two classes (Architecture Q9)

CVA is technically defined for three or more classes, but biplotEZ permits two-class CVA. The package supports this; the limitation is documented in `bl_build_projection()` help. With a `bl_model`, CVA uses the four prediction-outcome groups (TP/TN/FP/FN) by default, as in the loan example in the vignette and the development harness. If a group is empty (for example, the model makes no false positives on the training data), `bl_build_projection()` names it in a message and CVA uses the remaining groups. Empty levels, derived or in a user-supplied `cva_classes`, are dropped before CVA and before `W`, so its denominator `n - g` counts only groups with rows. `point_col` uses the confusion palette for any subset of the four labels. Two-group CVA arises only with `cva_classes = as.factor(class)` or a model-free `bl_build_result()`, and it warns. Within `bl_build_projection()`, `standardise` is forced to `FALSE` for CVA regardless of the user-supplied value, because biplotEZ performs its own within-class normalisation.

### 6.4 Cutoff parameter (Architecture Q10)

The `cutoff` parameter (default 0.5) is stored in `bl_result` and propagated through all downstream functions. Only `cutoff = 0.5` produces valid results under the current methodology. The parameter is retained to avoid breaking the interface in future extensions, but non-default values are clearly warned against in the documentation.

### 6.5 Hull polygon sourcing

The hull polygon in `bl_result` always comes from `bl_grid`, not from `bl_filter_result`. Reason: the filter polygon is constructed in a lightweight 2-PC space of the standardised training features, while the grid polygon is constructed in the final Z-space (which may be CVA, or PCA with different `proj_dims`). Only the grid polygon is consistent with the rendered biplot. `bl_assemble()` enforces this by reading the polygon from `bl_grid`.

### 6.6 Local rotation invalidates the hull polygon

The per-pair SVD rotation in `bl_find_local_cf()` produces a new Z-space for each eigenvector pair. The convex hull polygon from `bl_grid` is expressed in the original (unrotated) Z-space and is no longer geometrically meaningful after rotation. Therefore:

- Global search: hull polygon applied
- Local search: hull polygon **not applied**; only `train_ranges` (X-space bounds) and `set_filters` (actionability) constrain the search

This is the most important constraint difference between the two search modes.

### 6.7 Actionability filters (Manual §3D, Architecture Q8)

`set_filters()` exposes per-variable constraints that were deferred during initial architecture planning (Q8: "develop later"). These are Phase 3 only — they are not available in `bl_find_boundary()`. The `"fixed"` constraint allows a ±0.5 search window during boundary search (not strict equality) to avoid filtering out all contour points due to floating-point imprecision in the back-projection. After the search, `bl_find_local_cf()` sets each fixed feature it moved back to its observed value and keeps that point when it still crosses the boundary (see the fixed-feature restore in Section 4.8). In sparse CF generation, fixed variables always revert to the observed value regardless of their Shapley classification, because the intent of `"fixed"` is that the variable does not change in the final recommendation.

### 6.8 Shapley computation (Manual §3G)

The Shapley implementation adapts `1.2 Run_Shapley_optimized.R` (exact) and `4.4 Local Interpretation Shapley.R` (Supports/Contradicts classification). The exact algorithm is used when `p ≤ 14` (the default threshold), producing provably correct attribution. Beyond that, the permutation approximation is used with `M = 2048` samples by default. The Supports/Contradicts classification logic is class-direction-aware: for class-0 observations, positive Shapley values push toward class 1 (support crossing the boundary); for class-1 observations, negative values push toward class 0.

### 6.9 Custom model support (`bl_wrap_model`)

The instruction manual requires model-agnostic operation. The package achieves this via `bl_wrap_model()`: built-in raw-model types (e.g. a `mgcv::gam()` fit wrapped with `model_type = "GAM"`, predicted via `predict(type = "response")`), or `model_type = "custom"` with a user-supplied `predict_fn(model, new_data)`. The development harness uses the custom path for its first XGBoost model. The `predict_fn` is stored in `bl_model` and called uniformly via `.pred_function()` throughout the package.

### 6.10 Naming conventions

All exported functions except `plot_biplotEZ()` and `set_filters()` use the `bl_` prefix. S3 method naming follows R conventions (`print.bl_result`, `plot.bl_boundary`). Private helpers use a `.` prefix (`.build_hull_polygon`, `.bl_rotate`). Internal utility functions (`stop_if_*`, `calc_gini`) have no prefix as they are not user-facing. This aligns with instruction manual §7.4 and §9.4.

### 6.11 Post-selection feasibility in global search

`bl_find_boundary()` identifies the geometrically nearest contour point first, then checks whether it lies within `train_ranges`. The check is post-selection, not a pre-filter on contour segments. This means the boundary search always finds the mathematically nearest point and reports whether it is feasible — rather than excluding infeasible regions from the search geometry entirely. Out-of-range counterfactuals are kept and counted in a console message; the user sees them and can act on them rather than having them hidden.
